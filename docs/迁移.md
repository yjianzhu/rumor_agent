# 部署迁移注意事项

数据库与图片目录的备份/恢复见 `README.md` 的「数据迁移 / 备份恢复」章节。本文档覆盖**除此之外**的部署事项，按优先级排列。

反代与域名由 Caddy 处理，HTTPS / gzip / 证书续签等不在本文档范围。服务器在境外，CDN 资源（tailwind / htmx / google fonts）保持现状即可。

---

## 🔴 必须解决

### 1. 接口鉴权（首要安全问题）

当前 `src/api/api_routes.py` / `partial_routes.py` / `page_routes.py` 中所有路由仅 `Depends(get_db_session)`，**没有任何身份验证**。一旦绑定公网，任何访问者都能改 status / 发布 / 上传媒体。

**已决策**：由 Caddyfile 在反代层做 basicauth + 路径匹配，本文档不展开。

供 Caddyfile 撰写参考的路由清单：

| 路径 | 方法 | 性质 |
|---|---|---|
| `/` | GET | 公开站列表（按 `?include_unpublished=1` 切后台） |
| `/rumors/{slug}` | GET | 后台详情 + 审核表单 |
| `/admin` | GET | 后台入口（nav 链接） |
| `/partials/*` | GET/POST | htmx 局部刷新 + 媒体上传 |
| `/api/rumors/{slug}` | GET | 公开 JSON |
| `/api/rumors/{slug}` | PATCH | **写**：审核字段更新 |
| `/api/stats`、`/api/tags` | GET | 公开 JSON |
| `/p/*` | GET | 公开站（`public_routes.py`） |
| `/media/*` | GET | 静态图片 |
| `/static/*` | GET | 静态资源 |
| `/docs`、`/openapi.json` | GET | FastAPI 自带文档 |

需要保护的至少包括：所有 `PATCH`、`/partials/*` 的 POST、`/admin`、`/rumors/{slug}` 的审核表单页、`/docs`。

### 2. `config.toml` 不在 git 里

`.gitignore` 排除了 `config.toml`，里面包含 LLM API Key、DB 密码、XHS MCP URL 等敏感项。`git pull` 不会同步，必须 `scp` / `rsync` 单独传输，权限收紧到 `chmod 600`。

### 3. CORS 当前为通配

`src/api/app.py:13` 是 `allow_origins=["*"]`。公网部署时收紧到自己的域名（或干脆删掉中间件，反代同源不需要）。

## 🟡 服务运行形态

### 4. 启动命令

`scripts/run_server.py` 是开发用的（`127.0.0.1` + `reload=True`），生产用：

```bash
uv run uvicorn src.api.app:app --host 127.0.0.1 --port 8000 --workers 2
```

绑回环即可，公网入口由 Caddy 提供。

### 5. `MEDIA_DIR` 是相对路径

`config.toml` 默认 `media_dir = "media"`，`src/api/app.py:18` 用 `Path(settings.MEDIA_DIR).exists()` 判断后才挂载。

**陷阱**：如果进程的工作目录不是项目根，`/media/*` 会**静默不挂载**，所有图片 404 但服务本身正常启动。

systemd unit 必须写 `WorkingDirectory=/opt/rumor_agent`（或换成绝对路径 `media_dir = "/opt/rumor_agent/media"`）。

### 6. systemd unit 模板

```ini
# /etc/systemd/system/rumor-agent.service
[Unit]
Description=Rumor Agent Web
After=network.target postgresql.service

[Service]
Type=simple
User=rumor
WorkingDirectory=/opt/rumor_agent
ExecStart=/home/rumor/.local/bin/uv run uvicorn src.api.app:app --host 127.0.0.1 --port 8000 --workers 2
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### 7. Pipeline 调度

`--schedule` 是 in-process 前台循环，重启就丢，**不要在生产用**。改用 systemd timer 或 cron 跑 `--run-pipeline`，README line 281-289 有 cron 示例。

systemd timer 模板：

```ini
# /etc/systemd/system/rumor-pipeline.timer
[Unit]
Description=Rumor pipeline every 2h

[Timer]
OnBootSec=10min
OnUnitActiveSec=2h
Persistent=true

[Install]
WantedBy=timers.target
```

```ini
# /etc/systemd/system/rumor-pipeline.service
[Unit]
Description=Rumor pipeline one-shot
After=rumor-agent.service

[Service]
Type=oneshot
User=rumor
WorkingDirectory=/opt/rumor_agent
ExecStart=/home/rumor/.local/bin/uv run python -m src.main --run-pipeline
```

## 🟡 外部依赖与跨平台

### 8. 暂时放弃 XHS 采集

**已决策**：首次部署不带 XHS，后续再补。

需要做的：

- `cli_tools/xiaohongshu-mcp*` 不用 rsync 到服务器。
- `config.toml` 里 `[xhs]` 段保留默认值即可（`mcp_url = "http://127.0.0.1:18060/mcp"`），不会自动启动什么。
- **关键**：`run_pipeline()` 仍然会对每个关键词调一次 `collect_xhs(kw)`，由于 MCP 服务不存在，每次都会抛 `ConnectionError`。`src/main.py:run_pipeline` 已经做了软失败（`collect_failures` 列表 + warning log），不会阻塞 bili 链路。

后果：每次 pipeline 跑完 `logs` 里会多一条 `Pipeline xhs: ... failed` 警告。可以接受就先这样跑；嫌噪声大就在 `src/main.py:run_pipeline` 临时注释掉 XHS 那段（约 line 700-707）。

后续启用 XHS 时：

- 编译 Linux 版 `xiaohongshu-mcp`（`cli_tools/xiaohongshu-mcp/` 是 Go 源码）
- 在能访问的机器跑 `xiaohongshu-login` 拿 `cookies.json`，scp 到服务器
- 用 systemd 守护 MCP 进程，监听 `127.0.0.1:18060`
- cookies 定期刷新

### 9. `data/` 不在 git

`.gitignore` 排除了 `data/`。`data/staging/` 的历史 raw / candidate JSONL 不影响新部署运行，可选传：

```bash
rsync -avz data/ user@server:/opt/rumor_agent/data/
```

服务首次启动时 `data/staging/{raw,candidates}` 目录会按需创建。

### 10. `curl-cffi` 在 Linux 需要 build 依赖

`uv sync` 时如果 `curl-cffi` 编译失败，装：

```bash
apt install -y gcc libcurl4-openssl-dev libssl-dev python3-dev
```

通常 Python 3.12 有预编译 wheel，不一定真触发本地编译。先 `uv sync` 看报错再说。

### 11. PostgreSQL 扩展

目标机器必须有 `pgvector` 与 `uuid-ossp`。`pgvector` 在 Debian/Ubuntu：

```bash
apt install postgresql-16-pgvector  # 版本号匹配 pg
```

后续步骤（`CREATE EXTENSION` / `pg_restore`）参考 README。

### 12. Bilibili API cookie

`bilibili_api.comment.get_comments` 不带 cookie 长期拉热评会被风控。生产建议：

- 拿一个小号的 `SESSDATA` cookie
- 在 `config.toml` 加配置（当前代码未支持，需要扩展 `bilibili_collector.py`）

短期不配也能跑，但失败率会随频次上升。

## 🟢 运维细节

### 13. 日志走 journald

**已决策**：不走 `logs/*.log` 文件 + logrotate，直接交给 journald 管理。

当前代码状态（已查证）：

- `src/logger.py:configure_logging()` 同时添加 stderr handler 和 `logs/rumor_agent.log` FileHandler。
- **FastAPI web 服务不调用 `configure_logging()`**，日志由 uvicorn 自己的 logger 输出到 stderr，systemd 自动捕获到 journald —— web 这块开箱即用。
- **`src/main.py` (CLI / pipeline) 在第 176 行调用 `configure_logging()`，会同时写 stderr 和 `logs/rumor_agent.log` 文件**。systemd timer 跑 pipeline 时 stderr 进 journald，但**文件也会持续增长**，这就是要解决的点。

需要做的（部署前改）：

把 `src/logger.py` 的 `configure_logging()` 里 `_file_handler()` 那行去掉，或改为环境变量条件加载：

```python
import os

def configure_logging(level: int | str = logging.INFO) -> None:
    root = logging.getLogger()
    if root.handlers:
        return
    root.setLevel(level)
    root.addHandler(_build_handler(sys.stderr))
    if os.getenv("RUMOR_AGENT_LOG_FILE") == "1":
        root.addHandler(_file_handler())
```

prod 不设这个变量即可。开发本地想要文件日志时设 `RUMOR_AGENT_LOG_FILE=1`。

查看日志：

```bash
journalctl -u rumor-agent -f          # web 服务实时
journalctl -u rumor-pipeline -e       # pipeline 最近一次
journalctl -u rumor-agent --since "1 hour ago"
```

journald 自身的容量上限由 `/etc/systemd/journald.conf` 的 `SystemMaxUse=` 控制，默认 4G 上下，按需调。

### 14. `init_db.py` 防误操作

README 已注明走 drop & recreate 流程。**部署到 prod 后绝对不要再跑这个脚本**，会清空数据。建议在脚本开头加环境变量保护：

```python
if os.getenv("RUMOR_AGENT_ALLOW_DROP") != "1":
    raise SystemExit("Refusing to drop in unsafe env. Set RUMOR_AGENT_ALLOW_DROP=1 to confirm.")
```

prod 永远不设这个变量。

### 15. CORS 中间件回顾

如果同域部署（Caddy 反代同源），`CORSMiddleware` 可以直接删除整段，省一层处理。
